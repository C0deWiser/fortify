# Deleting passkey

When user deletes passkey in app (action DELETE user/passkeys/{id}) — is it 
possible to remove passkey from device too?

---

## Answer

**No — it is not possible.** WebAuthn gives a relying party no way to delete a credential from
an authenticator. There is no `PublicKeyCredential.delete()` and no
`navigator.credentials.delete()`; the Credential Management API that would have provided this
was drafted but never shipped, and WebAuthn Level 3 still has no deletion method.

`DeletePasskey` does as much as is possible — delete the row, dispatch an event:

```
vendor/laravel/passkeys/src/Actions/DeletePasskey.php:18
    $passkey->delete();
```

That is the whole of the server-side capability.

### What deletion does achieve

**The passkey is revoked.** The stored public key is gone, so the device's signature can no
longer be verified and the credential can no longer authenticate. The security-relevant goal
is met.

**But the credential stays resident on the device** — in iCloud Keychain, Google Password
Manager, the platform password manager, or on a roaming security key. It remains visible in
the OS password UI under your site's name, it remains synced to the user's other devices, and
it simply no longer works.

So deletion is effective, but incomplete: the server revokes, the device retains.

### The consequence worth planning for

`GenerateVerificationOptions::allowCredentials()` builds the allowed list from the user's
stored passkeys, so on the **confirm / password-confirmation / 2FA** path a deleted passkey is
correctly excluded. But for **passwordless login** the user is not yet known, so the list is
empty:

```
vendor/laravel/passkeys/src/Actions/GenerateVerificationOptions.php
    public function allowCredentials(?PasskeyUser $user): array
    {
        if (! $user instanceof PasskeyUser) {
            return [];   // authenticator falls back to discoverable credentials
        }
        ...
    }
```

An empty `allowCredentials` instructs the authenticator to use **discoverable credentials**,
and a deleted passkey is still discoverable. The user can therefore still select it on the
login screen and receive:

> Passkey not recognized. It may have been removed from your account.

which is the same response a legitimately removed passkey produces. This is inherent to
username-less passkey login — the server cannot enumerate credentials for a user it has not
identified yet — so it is not configurable away.

### Closest mechanisms that exist, and why none of them help

| Mechanism | What it does | Why it is not deletion |
| --- | --- | --- |
| `navigator.credentials.preventSilentAccess()` | Forces the next assertion to be user-interactive instead of silent | Nothing is removed; only the silent path is closed |
| Synced providers (iCloud Keychain, Google Password Manager) | Deleting on one device propagates to the others | Requires the *user* to delete it; the RP cannot signal it |
| Rejection-driven cleanup prompts | Some providers offer "remove this passkey?" after repeated RP rejection | Not standardized, not guaranteed, must not be relied upon |

### Recommendation

Deletion should tell the user to remove the credential from their password manager themselves,
and the message should be platform-aware:

- iOS / iPadOS — Settings → Passwords → edit the entry → Delete
- macOS — System Settings → Passwords
- Windows — Credential Manager (Windows Hello entries)
- Android — Google Password Manager → Passkeys

One point in the implementation's favour: `excludeCredentials()` in
`GenerateRegistrationOptions` is built only from *stored* passkeys, so a deleted credential
does not block re-registration on the same device. The residual annoyance is that the user may
end up with two entries for the site in their password manager, the older one permanently
dead.

### Summary

Deleting the server record is the only deletion possible, and it is sufficient to revoke the
passkey. Cleaning up the device copy is out of the RP's control and must be delegated to the
user through clear, platform-specific instructions.
